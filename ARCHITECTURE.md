# Architecture

## System name

spark-tutor

## Purpose

spark-tutor is a RAG-based AI chat system for training and education centers.

It provides AI-assisted learning workflows for learners and teachers while restricting retrieved knowledge to the user’s assigned training/class.

## Core services

### Frontend

Technology:

- React
- Vite

Responsibilities:

- Login/logout UI
- Password change UI
- Chat UI
- Attachment upload UI
- User settings UI
- Rendering assistant responses
- Showing workflow-specific results

Must not own:

- Business rules
- RAG filtering
- Prompt construction
- Auth decisions
- Workflow routing decisions

### Retriever backend

Technology:

- Python
- FastAPI

Responsibilities:

- Serve user-facing API
- Authenticate users
- Own chat/message APIs
- Own user settings APIs
- Run workflow routing
- Build workflow-specific prompts
- Call retriever logic
- Call chat LLM
- Enforce training/class filters
- Serve built frontend in user deployments

Must not own:

- Admin-only embedding ingestion UI unless protected
- Direct unrestricted vector access
- Public sign-up

### Embedder backend

Technology:

- Python
- FastAPI

Responsibilities:

- Admin-only document ingestion
- Chunking documents
- Calling embedding LLM
- Storing embeddings
- Tagging documents/chunks by training/class ID
- Updating knowledge base content

Must not be exposed to normal users.

### Database

Technology:

- PostgreSQL
- Vector extension

Responsibilities:

- Persist users
- Persist training/class mappings
- Persist user settings
- Persist chats and messages
- Persist attachment metadata
- Persist documents/chunks/embeddings
- Support vector search with metadata filtering

### Model runtime

Technology:

- Docker Model Runner

Responsibilities:

- Run chat LLM
- Run embedding LLM

## Deployment model

### Local development/test

Docker Compose starts all required services locally.

### Production

Production is intended to run centrally on servers.

Normal users should access only the web UI/API.

Admin-only ingestion and embedding must be protected.

## Main request flow

```txt
User prompt
  -> Frontend
  -> Retriever backend
  -> Auth/session validation
  -> Load user, settings, class/training ID, chat history
  -> Workflow router
  -> Workflow-specific prompt builder
  -> RAG retrieval scoped by class/training ID
  -> Chat LLM
  -> Persist messages and metadata
  -> Response to frontend
```

## AI workflows

### Socratic tutoring

Goal:

Guide the learner through questions and reasoning instead of directly giving away the answer too early.

### Teacher-support questions

Goal:

Help teachers generate good questions to ask learners.

### Exercise generation and solution verification

Goal:

Generate exercises or verify a submitted solution, including solutions to exercises not generated by spark-tutor.

### Topic teaching

Goal:

Teach a topic directly using clear explanations, examples, and course-specific context.

## Domain boundaries

### Auth domain

Owns:

* Login
* Logout
* Password change
* Password hashing
* Session/token handling
* User identity

### User domain

Owns:

* User profile
* Training/class assignment
* User settings
* Personalization options

### Chat domain

Owns:

* Chats
* Messages
* Chat ownership
* Chat history retrieval

### AI workflow domain

Owns:

* Workflow routing
* Prompt selection
* Prompt building
* AI behavior configuration
* Workflow metadata

### RAG domain

Owns:

* Query construction
* Retrieval
* Class/training filtering
* Chunk ranking
* Context packaging

### Knowledge ingestion domain

Owns:

* Admin document ingestion
* Chunking
* Embedding
* Tagging
* Knowledge base updates

### Attachment domain

Owns:

* Upload validation
* Attachment metadata
* Parsing
* Temporary file handling
* Passing parsed content to workflows

## Critical invariants

* Every chat belongs to exactly one user.
* A user belongs to exactly one training/class in the first version.
* RAG retrieval must always be filtered by training/class ID.
* Normal users must not access embedder/admin ingestion.
* User settings must not override safety or access-control rules.
* LLM output must not be trusted as authorization logic.
* Attachments are untrusted input.

* user_settings

* messages
* attachments
* documents

* embeddings
* workflow_runs

## Testing strategy

Unit tests

* Workflow router
* Prompt builders
* RAG filters
* Password validation
* User settings validation

Integration tests

* Login/logout/password change
* Chat creation and persistence
* Prompt-to-response flow
* Attachment flow
* Retrieval scoped by class/training ID

Security/access tests

* User cannot read another user’s chat
* User cannot retrieve another class’s documents
* Normal user cannot access embedder endpoints
* Passwords are never stored as plaintext
